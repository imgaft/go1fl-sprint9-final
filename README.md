# Поиск максимального значения в большом массиве данных

Итоговое задание модуля по многопоточности на Go. Программа сравнивает последовательный и параллельный поиск максимального элемента в слайсе из **100 000 000** случайных положительных целых чисел.

## Цель

Закрепить работу со слайсами, горутинами и `sync.WaitGroup`, научиться обрабатывать граничные случаи, писать unit-тесты и измерять производительность.

## Реализация

Весь основной код находится в `main.go`:

- `generateRandomElements(size int) []int` создаёт слайс заданной длины со случайными числами от 1 до 1 000 000 включительно. При `size <= 0` возвращает пустой слайс.
- `maximum(data []int) int` последовательно находит максимальный элемент. Для пустого слайса возвращает `0`; для непустого корректно работает в том числе с отрицательными значениями.
- `maxChunks(data []int) int` ищет максимум параллельно. Для слайсов короче восьми элементов используется `maximum`, чтобы избежать ненужного запуска горутин. В остальных случаях слайс делится на восемь непустых частей, по одной на горутину. Последняя часть получает остаток, если длина не кратна восьми. Каждая горутина записывает результат в собственную ячейку слайса максимумов; `sync.WaitGroup` обеспечивает ожидание всех вычислений. Затем `maximum` находит итоговый максимум среди восьми результатов.
- `main()` генерирует данные, запускает оба алгоритма на одном слайсе и выводит найденные максимумы и длительность поиска в микросекундах (`time.Now`, `time.Since`, `Microseconds`).

### Почему здесь нет гонки данных

Исходный слайс горутины только читают. Каждая горутина записывает результат в **отдельный индекс** слайса частичных максимумов. Главная горутина читает эти результаты только после `wg.Wait()`. Мьютекс для такого распределения записи не требуется.

## Запуск

Из корня проекта:

```bash
go run .
```

Программа должна вывести одинаковые максимальные значения для последовательного и параллельного поиска. Время зависит от компьютера и условий запуска.

## Тестирование

В `main_test.go` реализованы:

- `TestGenerateRandomElements` — длина результата, невалидный размер, диапазон случайных значений.
- `TestMaximum` — `nil`, пустой слайс, один элемент, возрастающие и убывающие значения, повторы, отрицательные и смешанные числа.
- `TestMaxChunks` — те же важные граничные случаи, включая размер меньше восьми, ровно восемь элементов и длину с остатком.
- `TestMaximumEqualsMaxChunks` — сравнение результатов обоих алгоритмов на слайсах разных размеров.
- `BenchmarkMaximum` и `BenchmarkMaxChunks` — сравнение производительности на одинаковом объёме данных (1 000 000 элементов) с помощью `testing.B` и `b.Loop()`.

Команды проверки:

```bash
gofmt -w main.go main_test.go
go test -v ./...
go test -race ./...
go vet ./...
go test -run '^$' -bench=. -benchmem -count=5
```

## Результаты на MacBook Air M2

Проверка выполнена на macOS, Apple M2, Go 1.27.4 (`darwin/arm64`). Все unit-тесты и проверка `-race` прошли; `go vet` не выдал замечаний.

### Основной запуск: 100 млн элементов

| Алгоритм | Найденный максимум | Время |
| --- | ---: | ---: |
| Последовательный | 1 000 000 | 245 225 мкс |
| 8 горутин | 1 000 000 | 13 406 мкс |

В этом конкретном запуске параллельный поиск оказался примерно в **18,3 раза быстрее**. Это не гарантированное ускорение: результаты зависят от кэширования, нагрузки на систему и других условий.

### Benchmark: 1 млн элементов, пять повторов

| Алгоритм | Время на операцию, примерно | Память на операцию | Аллокации |
| --- | ---: | ---: | ---: |
| Последовательный | 344–369 тыс. нс | 0 Б | 0 |
| 8 горутин | 185–187 тыс. нс | 848–858 Б | 18 |

В benchmark параллельный вариант быстрее примерно в **1,9 раза**, но создаёт дополнительные аллокации. Эти измерения показывают компромисс между скоростью вычислений и накладными расходами параллелизма.

## Вывод

Для больших наборов данных параллельная обработка может ускорить поиск максимума. Однако создание горутин имеет накладные расходы, поэтому на маленьких слайсах целесообразнее последовательный алгоритм. Для корректной работы важно дождаться завершения горутин и исключить конкурентную запись в одну и ту же область памяти. Производительность следует оценивать повторными benchmark-измерениями, а не по одному запуску.
